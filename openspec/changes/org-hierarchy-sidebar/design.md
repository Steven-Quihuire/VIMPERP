# Design: `org-hierarchy-sidebar`

> SDD design phase. Implements the proposal at `proposal.md` over the impact
> surface mapped in `exploration.md`. Follows `openspec/config.yaml` design
> rules: feature-first vertical slices, sequence diagrams for complex flows,
> and architecture decisions with rationale.

## 1. Overview

This design extends Vimcore's flat `Company → User` model to a fixed-depth
`Company → Division → Local → User` hierarchy with a **local-scoped catalog**,
while staying strictly backward compatible. `companyId` remains the tenant
root (`requireTenantCapability` is unchanged); `localId` is an additive
finer scope on top of it. The dashboard sidebar is trimmed to the three
working routes and gains an active-local switcher plus two new hierarchy
management routes.

The design is purely additive at the schema layer (new `divisions` table,
nullable columns only) and additive at the feature layer (a new
`org-hierarchy` feature slice; existing features gain nullable fields and
NULL-safe filters). A company with zero divisions and zero locals behaves
identically to today — the regression guarantee.

## 2. Schema Design

All schema changes live in `apps/api/src/shared/infrastructure/db/schema.ts`.
The migration is generated by `drizzle-kit generate` as `0012_*`.

### 2.1 New `divisionsTable`

```ts
export const divisionsTable = pgTable(
  'divisions',
  {
    id: text('id').primaryKey(),
    companyId: text('company_id')
      .notNull()
      .references(() => companiesTable.id),
    name: text('name').notNull(),
    createdAt: timestamp('created_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
  },
  (table) => [
    uniqueIndex('divisions_company_name_idx').on(table.companyId, table.name),
  ],
);
```

- `id` text PK (matches `branchesTable`/`membershipsTable` id style).
- `companyId` NOT NULL with FK→`companiesTable` (division is always company-scoped).
- Unique index on `(companyId, name)` enforces "name unique within company".

### 2.2 `branchesTable` → `locals`

Keep the existing table and columns; add a nullable `divisionId`. Reinterpret
existing rows as company-level locals (`divisionId NULL`).

```ts
export const branchesTable = pgTable('branches', {
  id: text('id').primaryKey(),
  companyId: text('company_id').notNull(),
  name: text('name').notNull(),
  locale: text('locale'),
  divisionId: text('division_id').references(() => divisionsTable.id),
});
```

> **Naming note:** The table column name stays `branches` to keep the
> migration purely additive and avoid renaming a physical table. The
> **domain** symbol becomes `Local` (see Section 4). `divisionId NULL` =
> company-level local.

### 2.3 `membershipsTable` — add nullable scope

```ts
export const membershipsTable = pgTable('memberships', {
  userId: text('user_id').notNull(),
  companyId: text('company_id'),
  role: authRoleEnum('role').notNull(),
  divisionId: text('division_id'),
  localId: text('local_id'),
});
```

- `divisionId` / `localId` are nullable, **no FK** — matches the existing
  pattern (`companyId` itself has no FK on this table; platform-admin
  memberships are intentionally unscoped). See ADR-4.

### 2.4 `itemsTable` — local-scoped catalog

Add nullable `localId`; change the unique index.

```ts
export const itemsTable = pgTable(
  'items',
  {
    id: uuid('id').defaultRandom().primaryKey(),
    companyId: text('company_id')
      .notNull()
      .references(() => companiesTable.id),
    localId: text('local_id'),
    categoryId: uuid('category_id').references(() => itemCategoriesTable.id),
    sku: text('sku'),
    name: text('name').notNull(),
    type: itemTypeEnum('type').notNull().default('product'),
    unit: itemUnitEnum('unit').notNull().default('unit'),
    unitPrice: numeric('unit_price', { precision: 12, scale: 2 })
      .notNull()
      .default('0'),
    tracksStock: boolean('tracks_stock').notNull().default(false),
    trackBatchMode: itemTrackBatchModeEnum('track_batch_mode')
      .notNull()
      .default('none'),
    deletedAt: timestamp('deleted_at', { withTimezone: true }),
    createdAt: timestamp('created_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
    updatedAt: timestamp('updated_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
  },
  (table) => [
    uniqueIndex('items_company_local_sku_idx')
      .on(table.companyId, table.localId, table.sku)
      .where(sql`${table.sku} IS NOT NULL`),
  ],
);
```

- The old `items_company_sku_idx` is **dropped** by the generated migration;
  the new `items_company_local_sku_idx` is created. `localId NULL` participates
  in the index (NULLs are distinct in PostgreSQL unique indexes by default,
  so multiple company-wide rows with NULL sku remain allowed, and the
  partial `WHERE sku IS NOT NULL` clause is preserved).
- No FK on `localId` — keeps membership/item scoping consistent and avoids a
  hard dependency on `branchesTable` for every item row.

### 2.5 `itemCategoriesTable` — local-scoped categories

```ts
export const itemCategoriesTable = pgTable(

      table.companyId,
      table.localId,
      table.parentId,
      table.name,

  ],
);
```

- Old `item_categories_company_parent_name_idx` dropped; new index created.

### 2.6 `userPreferencesTable` — active local

```ts
export const userPreferencesTable = pgTable('user_preferences', {
  userId: text('user_id').primaryKey(),
  activeCompanyId: text('active_company_id').references(
    () => companiesTable.id,
```

- `activeLocalId` nullable, no FK — matches `activeCompanyId` pattern shape

### 2.7 `auditEventsTable` — optional hierarchy context

```ts
export const auditEventsTable = pgTable(
  'audit_events',
  {
    id: text('id').primaryKey(),
    actorUserId: text('actor_user_id').notNull(),
    companyId: text('company_id').notNull(),
    divisionId: text('division_id'),
    localId: text('local_id'),
    type: text('type').notNull(),
    correlationId: text('correlation_id'),
    entityType: text('entity_type'),
    entityId: text('entity_id'),
    details: jsonb('details').notNull(),
    oldValues: jsonb('old_values'),
    newValues: jsonb('new_values'),

      table.companyId,

```

- `companyId` stays NOT NULL (cross-cutting audit queries depend on it).
- `divisionId` / `localId` nullable; populate when the audited action
  happens inside a scoped context. New index on `localId` for local-filtered
  audit queries.

## 3. Migration Strategy

- **Tooling:** `pnpm --filter api drizzle-kit generate` produces
  `apps/api/src/db/migrations/0012_<auto_name>.sql` plus the journal entry.
  No hand-written SQL edits — matches the existing 0000–0011 pattern.
- **Strictly additive:** new `divisions` table; new nullable columns on
  `branches`, `memberships`, `items`, `item_categories`, `user_preferences`,
  `audit_events`. No `NOT NULL`, no drops of existing columns, no renames.
- **Index changes:** the generated migration MUST include `DROP INDEX`
  for `items_company_sku_idx` and `item_categories_company_parent_name_idx`
  followed by `CREATE UNIQUE INDEX` for the new composite indexes. Drizzle
  Kit detects changed index definitions and emits both statements. Verify
  the generated SQL contains the `DROP INDEX` statements before apply.
- **Existing rows:**
  - `branches` rows: stay as-is, reinterpreted as company-level locals
    (`divisionId NULL`). No read path exists today, so the reinterpretation
    is low-risk (ADR-7).
  - `items` / `item_categories` rows: `localId` defaults to NULL =
    company-wide. No data migration needed; existing SKU uniqueness is
    preserved under the new `(companyId, localId NULL, sku)` index.
  - `memberships` rows: `divisionId`/`localId` NULL = company-level
    membership. Existing capability derivation is unchanged.
- **Rollback:** a reverse migration that drops the new nullable columns and
  the `divisions` table is safe — no data loss in pre-existing rows. Code
  rollback reverts routes/feature slices; old sessions still resolve because
  new fields default NULL and `localId IS NULL` queries behave as today.

### 4.2 Application use cases

`application/create-division.ts`, `list-divisions.ts`, `update-division.ts`,
`delete-division.ts`, `create-local.ts`, `list-locals.ts`, `update-local.ts`,
`delete-local.ts`. Each is a factory function `(deps) => (input) => Promise<output>`

injection pattern as `drizzle-item.gateway.ts`. Insert rows generate text ids
(matching `branchesTable` style) — caller (use case) is responsible for id
generation if a specific format is needed; default is `crypto.randomUUID()`.

## 5. Feature Architecture — `identity-access` (MODIFIED)

### 5.1 Domain — `apps/api/src/features/identity/domain/auth.ts`

```ts
export type AuthMembership = {
  companyId: string | null;
  role: AuthRole;
  divisionId: string | null;
  localId: string | null;
};

export type AuthSession = {
  user: PublicAuthUser;
  memberships: AuthMembership[];
  activeCompany: ActiveCompany | null;
  activeLocalId: string | null;
  capabilities: AuthCapability[];

```

- `deriveAuthCapabilities` is **unchanged** (ADR-5). It already selects the
  membership by `companyId` and reads its role; the new nullable fields do
  not affect role derivation.
- `requireTenantCapability` returns `companyId` only — `localId` is read
  from `auth.activeLocalId` by the catalog use cases (see Section 6).

### 5.2 Application — `application/resolve-auth-session.ts`

- `resolveActiveCompany` is unchanged.
- Read `activeLocalId` from `userPreferences.activeLocalId` (nullable).
  On login the preference is null → `activeLocalId` defaults to null
  (spec: "users start at company level"). Add a new helper in the same file
  that resolves `activeLocalId` only when the active company matches the
  local's company (otherwise null — a stale preference is silently coerced
  to null rather than throwing).

```ts
const resolveActiveLocalId = async (
  userId: string,
  activeCompany: AuthSession['activeCompany'],
): Promise<string | null> => {
  if (!activeCompany) return null;
  const savedLocalId = await authIdentityGateway.findActiveLocalId(userId);
  if (!savedLocalId) return null;
  const local = await orgHierarchyGateway.findLocalById(savedLocalId);
  if (!local || local.companyId !== activeCompany.companyId) return null;
  return savedLocalId;
};
```

- The returned `AuthSession` gains `activeLocalId: resolveActiveLocalId(...)`.

### 5.3 Infrastructure — `infrastructure/drizzle-auth.gateway.ts`

- `listMemberships` selects the new `divisionId`, `localId` columns.
- `findActiveCompanyId` unchanged.
- Add `findActiveLocalId(userId): Promise<string | null>` reading
  `userPreferences.activeLocalId`.
- Add `setActiveLocalId(userId, localId: string | null): Promise<void>`
  writing `userPreferences.activeLocalId` (null clears it).
- `setActiveCompanyId` should clear `activeLocalId` (switching company
  invalidates the previous local scope).

### 5.4 Presentation — `presentation/auth.router.ts`

`authSessionSchema` Zod gains the new fields:

```ts
const authMembershipSchema = z.object({
  companyId: z.string().min(1).nullable(),
  role: z.enum(['platform-admin', 'company-owner', 'company-user']),
  divisionId: z.string().min(1).nullable(),

const authSessionSchema = z.object({

  memberships: z.array(authMembershipSchema),
  activeCompany: z
    .object({ companyId: z.string().min(1), status: z.enum(['active', 'suspended', 'provisioning_failed']) })
    .nullable(),
  activeLocalId: z.string().min(1).nullable(),
  capabilities: z.array(z.enum(['catalog.read', 'catalog.write', 'catalog.delete'])),
});
```

New endpoint `POST /auth/me/active-local` mirrors the existing
`POST /auth/me/active-company`:

```ts
const switchActiveLocalBodySchema = z.object({
  localId: z.string().min(1).nullable(),
});

router.post('/auth/me/active-local', requireAuth, requireRole('company-owner', 'company-user'), async (req, res, next) => {
  try {
    const body = switchActiveLocalBodySchema.parse(req.body);
    const auth = (res.locals as AuthenticatedResponseLocals).auth;
    if (!auth.activeCompany) { res.status(400).json({ code: 'ACTIVE_COMPANY_REQUIRED' }); return; }
    if (body.localId !== null) {
      const local = await orgHierarchyGateway.findLocalById(body.localId);
      if (!local || local.companyId !== auth.activeCompany.companyId) {
        res.status(400).json({ code: 'LOCAL_NOT_IN_COMPANY' }); return;
      }
    }
    await switchActiveLocal({ userId: auth.user.id, localId: body.localId });
    res.status(204).send();
  } catch (error) { next(error); }
});
```

### 5.5 Shape-equality lockstep test

`apps/api/src/features/identity/presentation/auth-session-shape.test.ts`
imports the Zod `authSessionSchema` (API) and the web `AuthSession` /

`ItemCatalogGateway` and `CategoryGateway` add `localId: string | null` to

### 6.2 Infrastructure — `infrastructure/drizzle-item.gateway.ts`

Every method that today builds `eq(itemsTable.companyId, companyId)` adds
the NULL-safe local filter:

```ts
import { and, isNotNull, isNull, eq, desc, sql } from 'drizzle-orm';

const localFilter = (localId: string | null) =>
  sql`${itemsTable.localId} IS NOT DISTINCT FROM ${localId}`;

// In listItems:
where: and(eq(itemsTable.companyId, companyId), localFilter(localId), ...)
```

`IS NOT DISTINCT FROM` is NULL-safe: `NULL IS NOT DISTINCT FROM NULL` is
true, so `localId: null` matches company-wide rows only, and `localId: 'x'`
matches that local's rows only (spec §"Query scoping by active local").

`normalizeItemRows(rows, companyId, localId)` extends the TS-side defensive
filter to also re-check `row.localId IS NOT DISTINCT FROM localId`
(matches existing double-gate pattern; required by spec).

`toItem(row)` populates `localId: row.localId`. `toItemCategory(row)`
populates `localId: row.localId`.

`createItem` / `updateItem` / `createCategory` / `updateCategory` write the
`localId` from their input (sourced from `auth.activeLocalId`).

### 6.3 Application — use cases thread `activeLocalId`

`list-items.ts`, `get-item.ts`, `create-item.ts`, `update-item.ts`,
`soft-delete-item.ts`, `list-categories.ts`, `create-category.ts`,
`update-category.ts`:

- Each use case reads `companyId` and `localId` from the resolved auth
  session (the route handler passes `auth.activeLocalId` into the use case;
  the use case does NOT read `localId` from the request body — spec
  "Item creation with localId").
- `create-item` sets `localId = auth.activeLocalId` (null at company level).
- The existing audit-event write inside the gateway stays, and the audit
  row now carries the `localId` (and `divisionId` derived from the local's
  `divisionId` if present).

### 6.4 Tests — extend existing unit tests

`apps/api/src/features/items/infrastructure/drizzle-item.gateway.test.ts`
gains cases:
- Company-level list returns only `localId IS NULL` rows.
- Local-scoped list returns only that local's rows.
- SKU collision within company-wide vs a local is allowed (unique index
  per `(companyId, localId, sku)`).
- Defensive double-filter: rows with a wrong `localId` injected at the SQL
  layer are filtered out by `normalizeItemRows`.

## 8. Architecture Decision Records (ADRs)

### ADR-1: Fixed-depth adjacency list (Approach A) over single-table org_units or nested sets

**Decision:** Implement `Company → Division → Local → User` with a new
`divisions` table and `branches` (→`locals`) gaining a nullable `divisionId`.

**Rationale:** Matches the user's explicit hierarchy shape exactly. Avoids
recursive CTEs because depth is fixed at 3 (any query is a single join).
Stays backward compatible: nullable columns mean old rows, old
memberships, and old catalog keep working unchanged. Alternatives
(approach B single-table `org_units` with self-reference, approach C
nested sets) were rejected because they either break the `companiesTable`
identity and `requireTenantCapability` semantics (B) or are overkill for
fixed depth with no first-class Drizzle support (C). See exploration §"Approaches".

### ADR-2: Local-scoped catalog (items gain `localId`)

**Decision:** `items` and `item_categories` gain a nullable `localId`;
uniqueness moves to `(companyId, localId, …)`.

**Rationale:** The user explicitly chose local-scoped catalog over a
shared company-wide catalog. This is more complex (gateway filters,
defensive double-filter, index migration) but matches the business need
(each local can carry different products/prices). The backward-compatible
default (`localId NULL` = company-wide) preserves existing companies.

### ADR-3: Membership carries `divisionId`/`localId`

**Decision:** `membershipsTable` gains nullable `divisionId` and `localId`,
not just an `activeLocalId` preference.

**Rationale:** The user's explicit hierarchy requirement is `Company →
Division → Local → User`, where membership defines WHERE a user operates.
A membership with `localId` set means the user operates at that local; both
null means company-level. The `activeLocalId` *preference* is a separate
concern (which scope the user is currently viewing), controlled by
`POST /auth/me/active-local`.

### ADR-4: No FK on `memberships.divisionId`/`localId` (or `userPreferences.activeLocalId`, `items.localId`)

**Decision:** New nullable scope columns have no `.references()` FK.

**Rationale:** Matches the existing pattern — `membershipsTable.companyId`
itself has no FK (platform-admin memberships are intentionally unscoped).
Adding stricter FKs on the new columns would be inconsistent with the
existing integrity model. Integrity for `activeLocalId` and item `localId`
is enforced at the use-case layer (`switchActiveLocal` validates the local
belongs to the active company; item creation derives `localId` from the
session, never the request body).

### ADR-5: Roles stay company-level

**Decision:** `deriveAuthCapabilities` is unchanged. No
`division-manager` / `local-manager` roles.

**Rationale:** The user explicitly chose company-level roles. The active
membership is selected by `companyId` and its `role` determines capabilities;
`divisionId`/`localId` on the membership scope WHERE the user operates, not
WHAT they can do. `requireTenantCapability` continues to return `companyId`
as the tenant root; `localId` is a finer scope on top.

### ADR-6: Onboarding unchanged in v1

**Decision:** `OnboardingDraft`, `onboardingSteps`, and
`createPayloadFingerprint` do not gain hierarchy fields in this change.
Hierarchy is managed post-onboarding via the new `/divisions` and `/locals`
endpoints.

**Rationale:** Hierarchy capture during onboarding would significantly grow
onboarding complexity (new steps, new validation, idempotency fingerprint
changes that break replay-equality across payload shapes). The user scoped
this out. The idempotency-fingerprint collision risk noted in exploration
§3 is therefore moot for v1.

### ADR-7: `branchesTable` reinterpreted as `locals`

**Decision:** Keep the physical `branches` table; add nullable `divisionId`;
the domain symbol becomes `Local`.

**Rationale:** `branchesTable` is write-only seed data with no API, no
repository port, no UI, and no read path outside `createCompany` and tests.
Reinterpreting existing rows as company-level locals (`divisionId NULL`) is
therefore low-risk on the read path; the one write site (`createCompany`
inside `drizzle-company.gateway.ts:117-126`) must change in the same
transaction to insert into the new hierarchy-aware shape (or simply keep
seeding locals at company level). Keeping the physical table avoids a
destructive rename migration.

## 9. Risk Mitigation

| Risk | Mitigation |
|---|---|
| **Auth Zod ↔ web domain drift** | A shape-equality test
  (`auth-session-shape.test.ts`) is mandated by spec and implemented in
  this design (§5.5). Adding a field to one side without the other fails
  `pnpm test`. |
| **Item unique index change** | The generated `0012_*` migration MUST
  `DROP INDEX items_company_sku_idx` and
  `item_categories_company_parent_name_idx` before creating the new
  composite indexes. The design instructs the apply phase to verify the
  generated SQL contains the `DROP INDEX` statements before running apply. |
| **Defensive double-filter on items** | Both gates (SQL `WHERE companyId AND localId IS NOT DISTINCT FROM ?` and TS `normalizeItemRows`) MUST include `localId` or scoping silently leaks. The unit tests (§6.4) explicitly inject a wrong-`localId` row and assert `normalizeItemRows` filters it out. |
| **Stale `activeLocalId` after company switch** | `setActiveCompanyId` clears `activeLocalId` (§5.3). `resolveActiveLocalId` (§5.2) also re-validates that the persisted local belongs to the active company and coerces to null otherwise. |
| **Review-size budget (>400 lines)** | Per proposal, ship in chained PRs: schema+API / catalog / UI. The apply phase will group tasks accordingly. |
| **Prompt said 6 placeholders, code has 5** | Remove the 5 actual placeholders; document the count in the apply task. |

## 10. Test Strategy

### 10.1 Unit tests (Vitest)

- `drizzle-org-hierarchy.gateway.test.ts` — division/local CRUD, name
  conflicts, deletion conflicts (count > 0 ⇒ conflict), re-parenting.
- `drizzle-item.gateway.test.ts` (extended) — local-scoped lists, SKU
  collision across locals vs company-wide, defensive-double-filter with a
  wrong-`localId` row, `IS NOT DISTINCT FROM` behavior for null localId.
- `drizzle-auth.gateway.test.ts` (extended) — `listMemberships` returns
  `divisionId`/`localId`; `setActiveLocalId` writes null; `setActiveCompanyId`
  clears `activeLocalId`.
- `resolve-auth-session` tests — `activeLocalId` defaults null on login;
  coerces to null when the preference points at a local of another company.

### 10.2 Integration tests (Supertest)

- `org-hierarchy.router.test.ts` — POST/GET/PATCH/DELETE divisions and
  locals; authorization (403 for `company-user` writing); 409 on conflict
  deletions; backward-compat empty-list for a company with no hierarchy.
- `auth.router.test.ts` (extended) — `POST /auth/me/active-local` happy
  path, clear path, 400 when local belongs to another company; `GET /auth/me`
  includes `activeLocalId` and membership `divisionId`/`localId`.
- `items.router.test.ts` (extended) — local-scoped list, item creation
  derives `localId` from session not body; company-level vs local-level
  isolation.

### 10.3 Shape-equality test

`auth-session-shape.test.ts` (§5.5) — explicitly compares
`authSessionSchema` Zod shape against the web `AuthSession`/`AuthMembership`
type fields. Required by the `identity-access` spec; adding a field on one
side without the other fails the build.

### 10.4 E2E (Playwright)

- **Regression**: company with no hierarchy behaves identically to today
  (sidebar shows 3 routes; items list returns the same rows; login lands
  at company level with `activeLocalId: null`).
- **Hierarchy creation flow**: `company-owner` creates a division, creates
  a local under it, re-parents the local, deletes both (with the conflict
  path attempted first).
- **Active-local switching**: `company-owner` switches active local from
  the sidebar; items page re-filters to the active local's items; clearing
  the active local restores company-wide items.

### 10.5 Quality gates

`pnpm test` (unit + integration + shape-equality), `pnpm build` (typecheck
across `apps/api` and `apps/web`), `pnpm --filter api test:coverage` (80%
threshold per `config.yaml`). ESLint and Prettier run as part of the build.
